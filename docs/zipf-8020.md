# Calibracion Zipf 80/20

## Definicion

Cada posicion es una palabra logica de 8 bytes. Para W bytes hay N=W/8
posiciones y el conjunto caliente son las primeras K=ceil(N/5), igual que
hot20_access_fraction del cliente. El rango k se asigna a (k-1)*8: las posiciones
populares son contiguas en direcciones bajas. No se reordena por frecuencias
observadas tras la corrida ni se escoge el 20% que mejor ajusta los resultados.
El porcentaje efectivo de posiciones K/N puede superar ligeramente el 20% por
redondeo; se registra en hot_fraction_effective. No es un porcentaje de bloques.

Zipf tiene P(k)=k^(-theta)/H_N(theta). Se busca el parametro que cumple
H_K(theta)/H_N(theta)=0.8. Por eso theta depende de W, pero no de B, capacidad
de cache, respaldo o semilla. Mantener W y theta fijos al comparar esos factores.
Al cambiar W, generar otra calibracion. theta=1.1 sigue siendo el valor por
defecto del cliente; no se cambia silenciosamente. Para obtener 80/20 hay que
pasar --zipf-theta con el valor del JSON correspondiente al W de la corrida.

## Calculo

scripts/calibrate_zipf.py usa biseccion en [0,2], con el extremo 0 como limite
uniforme y un resultado compatible con 0 < theta <= 2. Hace 60 iteraciones,
sin semillas ni resultados empiricos para elegir el parametro. Algunas
poblaciones muy pequenas no admiten el objetivo en ese intervalo; se rechazan
en vez de devolver una calibracion ficticia.

H_n se suma directamente hasta 4096 terminos con math.fsum. Para n mayor se
agrega la integral de x^(-theta), correccion de extremos y cuatro correcciones
Euler-Maclaurin (derivadas 1,3,5,7) sobre la cola. expm1 evita cancelacion cerca
de theta=1; en theta=1 la integral es logaritmica. El costo y memoria no crecen
linealmente con W. Es un calculo numerico de doble precision, no una suma exacta
de racionales. Las pruebas comparan contra sumas directas independientes hasta
100000 terminos, incluyendo theta=1 y valores cercanos.

El JSON contiene W, N, K, theta, probabilidad teorica esperada, metodo, version
del generador y mapeo de rangos. Los archivos se crean exclusivamente y no
sobrescriben calibraciones anteriores. Guardar el JSON utilizado en la campana.

## Verificacion empirica

src/zipf_probe.c enlaza el src/workload.c existente, igual que el cliente, sin
cache, respaldos ni una reserva proporcional a W. Cuenta accesos calientes y
calcula la misma huella de direcciones que el cliente. Es un verificador del
generador de direcciones, no un benchmark de latencia ni de trafico de red.

scripts/verify_zipf.py comprueba el JSON y ejecuta el probe con al menos tres
semillas distintas (por defecto 42,43,44), 200000 accesos por semilla y vuelve
a ejecutar la primera para comprobar repetibilidad de huella y conteos.
Acepta entre 100000 y 10000000 accesos por semilla. La semilla es uint64 y
admite cero. Se aplica un criterio fijo por semilla:

    abs(accesos_calientes / accesos_totales - 0.8) <= 0.01

Esto significa entre 79% y 81%, tolerancia de UN punto porcentual. No es un
error relativo de 1%. Una secuencia aleatoria finita no tiene por que dar
exactamente 80%. No se modifica theta al observar una corrida, no se escogen
solo semillas favorables ni se presentan estas pruebas como una certificacion
estadistica del PRNG. Un resultado fuera de tolerancia queda marcado como
fallido y el verificador devuelve estado 1; hay que investigarlo.

El informe registra configuracion, semillas, conteos enteros, fracciones,
error absoluto, hashes y passed. La repeticion de huellas se exige dentro de
la misma plataforma; las diferencias de libm entre plataformas siguen siendo
una limitacion documentada del muestreador. La prueba de integracion exige
que el probe y el cliente produzcan la misma huella para dos tamanos de bloque.

## Comandos Raspberry

```bash
make test-zipf
make test-zipf-ubsan
mkdir -p build/manual
python3 scripts/calibrate_zipf.py --working-set 16384 \
  --output build/manual/zipf-16k.json
python3 scripts/verify_zipf.py --config build/manual/zipf-16k.json \
  --probe ./build/zipf_probe --samples 200000 --seeds 42 43 44 \
  --output build/manual/zipf-16k-verificacion.json
```

Para aplicar la configuracion al cliente:

```bash
theta=$(python3 -c 'import json; print(json.load(open("build/manual/zipf-16k.json"))["theta"])')
./build/client --backend synthetic --pattern zipf --zipf-theta "$theta" \
  --seed 42 --block-size 4096 --cache-size 8192 \
  --working-set 16384 --accesses 200000
```

El hot20_access_fraction del cliente debe coincidir con observed_fraction del
informe para semilla 42, salvo redondeo de impresion. La tasa de aciertos puede
ser distinta: 80/20 describe direcciones solicitadas, no hits ni utilizacion.
Para la campana prevista de 256 MiB, preparar y verificar otra configuracion:

```bash
python3 scripts/calibrate_zipf.py --working-set 268435456 \
  --output configs/zipf-256m.json
python3 scripts/verify_zipf.py --config configs/zipf-256m.json \
  --probe ./build/zipf_probe --samples 200000 --seeds 42 43 44 \
  --output build/manual/zipf-256m-verificacion.json
```

Estas operaciones no reservan 256 MiB de datos ni necesitan un servidor remoto.
La comprobacion posterior de tiempos y respaldos a esa escala es otra etapa.
Si un nombre ya existe, usar otro para una nueva version; no borrar evidencia
previa para conseguir una salida aprobada.

## Pruebas

make test-zipf incorpora siete pruebas matematicas/CLI y tres de integracion C.
make test y make ubsan incluyen estos casos junto con todos los anteriores;
make test-zipf-ubsan ejecuta solo este modulo con UBSan. No se modifican los
archivos del generador, cliente, cache ni protocolo. make test-sd y B0 mantienen
su comportamiento previo. La nueva configuracion se aplica explicitamente.
